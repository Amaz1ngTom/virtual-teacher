# 性能实测记录

本文只记录可由项目日志复核的数据。项目中的“FLOAT实时率”定义为：

```text
视频（音频）总时长 ÷ FLOAT Worker纯推理时间
```

因此大于 `1` 表示视频生成速度快于播放速度。若使用部分论文和系统常见的反向定义
`处理时间 ÷ 视频时长`，则数值小于 `1` 表示快于实时。对外展示时应同时写清公式，
避免“RTF”定义相反造成误解。

## 2026-08-31：远程 RTX 4090 真实课程场景

- 场景：已发布的确定性课程“神经网络第一讲”首次生成。
- 配置：FLOAT原始模型，10 NFE，512×512，25 FPS，持久化Worker，十段串行队列。
- 段数：10。
- 视频/音频总时长：178.000秒。
- FLOAT累计纯推理时间：140.919秒。
- FLOAT实时率：`178.000 / 140.919 = 1.263×`。
- 反向处理因子：`140.919 / 178.000 = 0.792`。
- 实际体验：第一段就绪后连续播放十段，中间没有可感知等待。
- 本轮TTS累计耗时：51.054秒；FLOAT任务提交累计耗时：0.820秒；首个聊天请求
  总耗时约51.971秒。TTS和首段等待不计入上述FLOAT纯推理实时率。

## 较早的0.6×诊断结果为什么不作为正式成绩

较早的单任务诊断中，7.04秒音频在Worker预热后耗时11.587秒，实时率约0.608×；
另一次24.48秒音频耗时43.446秒，约0.563×。两次诊断期间共享服务器的整机
Load Average约75至114、CPU约65%至70%，Swap已分配满；当时没有同步记录推理期间
4号卡的功耗、频率以及各阶段耗时，因此无法把慢速唯一归因到某一环节。

可以确认的差异包括：

1. 早期诊断发生在共享主机高负载时，CPU预处理、图像解码和视频编码可能受到调度影响。
2. 7秒短视频更容易被每次调用固定开销影响，但这不能单独解释24秒样本同样偏慢。
3. 本次课程测试使用持续预热的Worker和连续任务队列，十段每段均快于实时，结果在
   用户实际播放中得到无缝衔接验证。
4. 因为早期没有完整资源采样，只能将0.6×视为一次异常环境诊断，不能表述为4090的
   稳定性能。

后续制作4060/4090对比表时，仍应在服务器负载较低时，用相同音频、参考图、NFE和
Worker版本各进行至少三次预热后测试，并同时记录CPU负载、GPU频率、排队时间和浏览器
首播等待。
